- [ ] **Rule-6 surgery: stop notifying and calling foreign components while holding locks** *(2026-08-17)* - two dump-proven deadlocks (both captured 2026-08-17 during scenario loads) came from lock-order cycles among `CoreViewModel.m_Lock`, `ProjectScenarioDisplaySettingsViewModel.m_Lock`, `GanttActivitySelectorViewModel.m_Lock` and ReactiveUI's internal `ExpressionChainSink` gates. The point fixes already landed: the lock-free getter sweep (ARCHITECTURE §7 rule 9), hoisting the display-settings core callbacks (`SetIsProjectScenarioUpdated`/`IsReadyToCompile`) out of all the setter lock blocks, and ref-counted revising guards in the Gantt/earned-value selectors (a shared bool let one reviser's `finally` clear the other's guard mid-revision across threads). The REMAINING call-out-under-lock sites are hardening, not live bugs - every remaining edge is one-way with the point fixes in place - and form the deferred surgery, in descending value: (1) `CoreViewModel.ProcessProjectScenario`/`ResetProjectScenario` hold `m_Lock` across the entire load fan-out: raising settings setters, raising `IsReadyToReviseTrackers` (whose `Scheduler.CurrentThread` subscriptions synchronously run selector revisions ON the raising thread, taking selector locks under the core lock - the Core→Selector edge in the first dump), and calling `DisplaySettingsViewModel.SetValues` (the Core→DS edge in the second dump); surgery = split each into a state phase under the lock and a fan-out phase after release, collecting pending raises/signals under the lock and emitting them outside - §7 rule 7 (handlers re-read live state; payloads are stale snapshots) is what makes raise-after-release semantically safe, and the `Begin`/`EndBulkUpdate` window wraps both phases so suppression semantics survive. (2) `ProjectScenarioDisplaySettingsViewModel.SetValues` assigns ~30 raising setters under the DS lock, so every synchronous observer (ReactiveUI sink gates) runs under it; surgery = set fields and collect changed property names under the lock, raise them all after release (this also collapses the setters' reentrant locking). (3) The five selector view models mutate `ObservableCollection`s inside their locked `Set*` methods, so `CollectionChanged` handlers (which raise, and in Gantt/EV write through to DS/Core) execute under the selector lock; surgery = detach the handler around locked mutations and do one manual refresh+raise after release, or compute the change set under the lock and apply it outside. (4) Chart-manager plot-model setters (earned-value/Gantt/resource charts) and `ResourceTrackerSetViewModel.RefreshIndex` raise inside their locks - trivial set-under-lock/raise-after splits. (5) Document the global lock-acquisition DAG in ARCHITECTURE §7 (Manager→Core→DisplaySettings, Core→Selector, node/tracker VMs as leaves; verify core never calls back into the scenario manager under its lock) so future cross-VM calls have an order to conform to. Adjacent smells noted while investigating: `GanttChartShowConnections`/`EarnedValueShowResources` are plain `List<int>` mutated by UI handlers without the DS lock while `SetValues` seeds them under it (torn-read risk), and DS setters mark the scenario dirty even when `RaiseAndSetIfChanged` is a no-op write. Related: the 2026-08-04 contention entry above - the getter sweep already delivered its "lock-free snapshots for hot bound properties" suggestion for the selector/tracker getters. **DIRECTION TO EXPLORE - delete locks rather than order them** *(2026-08-17)*: the reactive cascade itself is not the problem and does not need rewriting - in all three dumps the dependency graph behaved correctly and the failures were in the locking wrapped around it - but the current design is safe only by discipline, not by construction, because three properties combine badly: one lock per view model with cross-view-model calls made freely in both directions; synchronous notification (`PropertyChanged`/`CollectionChanged`) that re-enters arbitrary foreign code holding locks we neither own nor can inspect (ReactiveUI `ExpressionChainSink` gates, DynamicData, Dock); and `Scheduler.CurrentThread` subscriptions that run on whichever thread happened to raise, so "which thread executes this" is not statically knowable. The lock graph is therefore not fully knowable either, and a deadlock stays one refactor away no matter how carefully rules 6 and 9 are applied. Target end state: view models are UI-thread affine and hold NO locks at all, while background work (parse, compile, metrics) operates on immutable snapshots - as the compiler already does when it clones the graph - and returns a single result applied on the UI thread; with no locks there is no lock order to get wrong and rule 9 becomes unnecessary rather than merely enforced. Pragmatic 80% if full affinity proves too invasive on the load path: exactly ONE lock at the Core/model boundary and none anywhere else, which (combined with rules 6 and 9) removes every cycle among our own locks by construction. The path is incremental and mostly already walked - the getter sweep permanently killed the first class, the setter hoists killed the live instance of the second, and once rule 6 holds everywhere most remaining view-model locks will be found to guard nothing but brief field writes that only ever happen on one thread, at which point they can be DELETED rather than ordered (strictly better than maintaining a documented lock DAG forever, and it subsumes item 5 above). Add mechanical enforcement instead of vigilance: `System.Threading.Lock` exposes `IsHeldByCurrentThread`, so debug-only assertions at the raise/callback boundaries turn a latent deadlock into a loud test failure rather than a dump weeks later - now split out as its own entry at the end of this file, because it is worth doing on its own terms and does not depend on any of the surgery above. Finally, the "third dump" (`zametek-deadlock-2.dmp`, 2026-08-17 - NOT a deadlock: no thread blocked on any lock, UI thread idle, while a scenario-load worker span inside `PriorityListResourceScheduler.CalculateResourceSchedules` with nothing ever scheduled onto any of the 14 resource builders) is no longer parked: the 2026-08-18 ClrMD analysis root-caused the spin as a torn `HashSet` clone poisoning the scheduler's `Contains` gate (ARCHITECTURE §7 rule 10 tells the full story and names the ProjectPlan-side race that tore it), the scheduler itself now detects the dead state upstream (Zametek.Maths.Graphs 3.2.0 reports compilation error C0020 instead of spinning, and `Compile` takes a cancellation token), and the app-side compile watchdog (`CompilationTimeoutMilliseconds`, 2026-08-19) bounds anything the scheduler cannot prove dead. The remaining structural item from that paragraph - run the compile outside the lock against a snapshot - is Phase 2 of the compile-on-snapshots entry below. **SIZED, AND A RECOMMENDATION NOT TO DO IT AS WRITTEN** *(2026-08-21)*: measured against the code as it stands, the surgery spans `CoreViewModel` (2,453 lines, 66 `lock (m_Lock)` sites, with the load fan-out itself around ninety lines held under a single lock containing two `SetValues` calls, four settings assignments that each raise and fan out, and the `IsReadyToReviseTrackers` write whose `Scheduler.CurrentThread` subscriptions run selector revisions synchronously on the raising thread), `ProjectScenarioDisplaySettingsViewModel` (735 lines, 33 lock sites, and a `SetValues` performing sixty property assignments every one of which goes through a locked raising setter), five selector view models totalling 1,455 lines, a handful of trivial chart-manager splits, and the documentation item. That is the largest open entry in this file, and the risk is worse than the line count implies, because the change is to WHEN notifications fire in a cascade that has already produced three dumps, verification means the CLI worktree diff plus GUI checking, and the lesson from the compile work is that naive concurrency tests have no teeth. Two things argue against doing it in this form. First, there is no live bug: the point fixes landed and every remaining edge is one-way, so all of the above is hardening. Second, this entry argues against itself - the DIRECTION TO EXPLORE immediately above makes items 1 to 4 unnecessary rather than done, and explicitly subsumes item 5, since with no locks there is no acquisition DAG to document; doing the ordering surgery first would be paying in full for something the better end state discards. Better value nearby: Phase 2b (run the compile outside `m_Lock`) is small and concrete now that compilation works on private copies. **What has changed the economics is the browser head** *(2026-08-21)*: single-threaded WebAssembly runs everything on the UI thread regardless, so "UI-thread affine, no locks, background work on immutable snapshots" is not a costly migration there - it is what the platform already imposes. - [ ] **Decide how the web app is hosted and deployed** *(2026-08-21)* - `dotnet publish` produces a static `AppBundle`, but nothing publishes it anywhere. Two requirements are already known and documented in the README: a secure context (HTTPS or localhost) for the browser APIs the file pickers need, and a `Service-Worker-Allowed: /` header on `_framework/sw.js` - or that script served from the site root - because Avalonia registers its service worker at the root scope and without it Firefox and Safari lose the save-file fallback. - [ ] **Reconsider single-threaded WebAssembly once the browser head does real work** *(2026-08-21)* - the browser head runs single-threaded, which is what lets it be served from any static host. The consequence is that every `Task.Run` in the view-model layer - and there are many, including `RunCompile` - executes on the UI thread, so a large plan's compile will freeze the tab, and the compile watchdog (`CompilationTimeoutMilliseconds`) probably cannot fire at all, since its timer callback has no thread to run on while a synchronous compile holds the only one. Neither has been measured yet; measure with a real plan before deciding. The alternative is `WasmEnableThreads`, which keeps `Task.Run` genuinely off the UI thread and restores the watchdog, at the cost of requiring COOP/COEP headers from the host (ruling out plain GitHub Pages) and a less well travelled Avalonia configuration. Related: the "delete locks rather than order them" direction in the rule-6 entry above becomes more attractive if the browser stays single-threaded, since a UI-thread-affine view model layer has nothing to contend over.

- [ ] **Stop the MSIX build depending on whether NuGet decides to restore** *(2026-08-21)* - the packaging build needs every project's `project.assets.json` to carry a target for each RID in the bundle, and `build-msix.ps1` arranges that by setting `RuntimeIdentifiers` in the environment so that restore populates all three in one pass. That only works if restore actually runs. When it does not - NuGet reports "All projects are up-to-date for restore" and keeps whatever assets file is already there - a file left behind by an ordinary `dotnet build`, which has no RIDs at all, survives, and the per-RID inner publish then fails with `NETSDK1047` naming a project that looks entirely innocent. Observed once during the `PlatformTarget` investigation, on `Zametek.ProjectPlan.Core`, immediately after a plain solution build; the run before and the run after both succeeded, which is what makes it look like flakiness rather than a missing input. Deleting `obj` in `-Clean` would force a restore and close it, and was tried on 2026-08-21, but it does not work: MSBuild evaluates every project before running any target and that evaluation imports `obj\<project>.nuget.g.props`, so against an empty `obj` the DesktopBridge targets fail with `MSB4024` looking for a file the same command is about to write. Splitting restore into its own invocation fixes that but then leaves the per-RID targets unpopulated, because the `RuntimeIdentifiers` environment variable does not reach a standalone `/t:Restore` the way it reaches the `/restore` switch; and passing it as a global property instead is worse still, since the per-RID inner publishes cannot then override it and the SDK rejects the whole list as a single identifier (`NETSDK1083`). All three failures are recorded in the script's comments so the next person does not walk the same three steps. What remains worth trying: `-p:RestoreForce=true` on the existing single invocation, which costs a few seconds of re-evaluation on a build already measured in minutes and would make the RID targets unconditional; or, cheaper and less certain, reading each referenced project's assets file up front and failing early with a message that names the real problem instead of letting `NETSDK1047` misdirect.

- [ ] **Audit the packaging path for more silently-inert code** *(2026-08-21)* - `-Clean` in `build-msix.ps1` never deleted anything from the day it was written: it used `Get-ChildItem -Path $dir -Include bin,obj -Directory`, and `-Include` filters the leaf of `-Path` rather than the children unless the path itself ends in a wildcard, so the pipeline matched nothing while the script cheerfully printed "Cleaned obj/bin". Nothing failed, which is precisely why it went unnoticed for a year - and it quietly invalidated every "clean build" anyone believed they had run, including the first comparison in the `PlatformTarget` investigation, where stale IKVM native staging made 64 files look as though a change to a managed compiler switch had rearranged the JDK. A second instance turned up almost immediately, in 349baed0: the WiX components were sourcing `$(var.<project>.TargetDir)publish\`, a directory the publish had stopped writing to, and nothing anywhere reported a missing input. The packaging projects sit outside the solution filter, so nothing in the gates builds or exercises them, and the same class of fault - a command or a path that appears to work because its failure mode is silence - could be sitting in the rest of that path. Worth a read-through of `build-msix.ps1`, the two `.wapproj` files and the WiX project with that specific suspicion in mind, and worth asking whether any of it can be brought under a gate.

- [ ] **The MSI installer can be built mislabelled, and nothing checks its inputs exist** *(2026-08-21)* - `Zametek.ProjectPlan.MsiPackager` declares `<Platforms>x86;x64;ARM64</Platforms>` and names its output `projectplandotnet.<version>.installer.$(Platform)`, and README's instructions say to set the platform to the architecture you want. Both component files now source their payload from `$(var.<project>.TargetDir)win-x64\publish\`, hard-coded (349baed0, fixing a path the publish had stopped writing to). Building the installer as x86 or ARM64 therefore produces a file *named* for that architecture containing x64 binaries, with no error at any point - the packager is happy, WiX is happy, and the mislabelling is only discoverable by installing it on the machine it was supposedly built for. Either drive the RID from `$(Platform)` so the two agree, or reduce `<Platforms>` to x64 alone and say plainly in the README that the MSI is x64-only; the present arrangement offers three choices and honours one. Related, and the reason this is easy to miss: the packager consumes a publish that nothing enforces. `readme.txt` asks for `make publish-desktop publish-cli ARCH=x64 OS=win` beforehand, but the project merely reads whatever is sitting in those folders, so a stale publish from a previous version - or none at all, if the folder still holds an older run - is indistinguishable from a fresh one. A guard that fails the build when the expected payload is absent or older than the referenced project's own output would turn all of this from silent into loud. The MSI is not built by CI or by the solution (`<Build Project="false" />` in the .slnx), so none of it is covered by any gate; see the packaging audit entry above.

- [ ] **Assert in Debug that no application lock is held when a change is announced** *(2026-08-21, extracted from the rule-6 entry as the piece worth doing on its own)* - the two 2026-08-17 deadlocks were both our own half of an ABBA: a thread raising `PropertyChanged` into a ReactiveUI expression-chain sink while holding a view model's `m_Lock`, against a thread inside that sink's gate re-reading a getter that wanted the same lock. Rules 6 and 9 forbid exactly that, and the point fixes removed the live instances, but nothing enforces the rules - no test, no analyzer, no gate - so the real risk is not the edges that exist today, which are one-way, it is a future edit quietly re-creating a cycle. A deadlock costs a frozen application with no exception, no log line and no crash, diagnosable only by capturing a process dump and reading it with ClrMD, which has already been done three times. `System.Threading.Lock` exposes `IsHeldByCurrentThread`, so a `[Conditional("DEBUG")]` assertion at the announcement boundary turns that entire failure mode into a test failure naming the offending line. It only ever sees our own locks, never ReactiveUI's or DynamicData's or Dock's - which is the point, because our half is the half we control and the half the rules govern. The seam is `ViewModelBase`, currently an empty class deriving from `ReactiveObject` and sitting between ReactiveUI and every view model; confirm whether ReactiveUI offers a suitable override there, and fall back to a small helper invoked at the raise sites if it does not. Scope to size first: 31 `Lock` fields across the view model layer, so the assertion needs a cheap way to ask "does this thread hold any of them" - either a registry of the locks in play, or each view model asserting only its own plus the shared leaf `m_ActivityDataLock`. The payoff is immediate rather than theoretical, because the pre-commit hook builds and tests in Debug and the suites drive real scenario loads and compiles through the whole cascade, so a violation would surface in the gates rather than in a dump weeks later. Note that this encodes rules that already exist rather than inventing new ones: rule 11 deliberately holds the leaf lock around an activity's writes and never around its announcements, and that is precisely the shape the assertion would be checking. Worth doing whether or not the rule-6 surgery above ever happens - and if the "delete locks rather than order them" direction is taken instead, these assertions are how you would prove each lock had actually become removable.
