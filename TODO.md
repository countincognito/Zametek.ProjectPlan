- [ ] **Rule-6 surgery: stop notifying and calling foreign components while holding locks** *(2026-08-17)* - two dump-proven deadlocks (both captured 2026-08-17 during scenario loads) came from lock-order cycles among `CoreViewModel.m_Lock`, `ProjectScenarioDisplaySettingsViewModel.m_Lock`, `GanttActivitySelectorViewModel.m_Lock` and ReactiveUI's internal `ExpressionChainSink` gates. The point fixes already landed: the lock-free getter sweep (ARCHITECTURE §7 rule 9), hoisting the display-settings core callbacks (`SetIsProjectScenarioUpdated`/`IsReadyToCompile`) out of all the setter lock blocks, and ref-counted revising guards in the Gantt/earned-value selectors (a shared bool let one reviser's `finally` clear the other's guard mid-revision across threads). The REMAINING call-out-under-lock sites are hardening, not live bugs - every remaining edge is one-way with the point fixes in place - and form the deferred surgery, in descending value: (1) `CoreViewModel.ProcessProjectScenario`/`ResetProjectScenario` hold `m_Lock` across the entire load fan-out: raising settings setters, raising `IsReadyToReviseTrackers` (whose `Scheduler.CurrentThread` subscriptions synchronously run selector revisions ON the raising thread, taking selector locks under the core lock - the Core→Selector edge in the first dump), and calling `DisplaySettingsViewModel.SetValues` (the Core→DS edge in the second dump); surgery = split each into a state phase under the lock and a fan-out phase after release, collecting pending raises/signals under the lock and emitting them outside - §7 rule 7 (handlers re-read live state; payloads are stale snapshots) is what makes raise-after-release semantically safe, and the `Begin`/`EndBulkUpdate` window wraps both phases so suppression semantics survive. (2) `ProjectScenarioDisplaySettingsViewModel.SetValues` assigns ~30 raising setters under the DS lock, so every synchronous observer (ReactiveUI sink gates) runs under it; surgery = set fields and collect changed property names under the lock, raise them all after release (this also collapses the setters' reentrant locking). (3) The four selector view models mutate `ObservableCollection`s inside their locked `Set*` methods, so `CollectionChanged` handlers (which raise, and in Gantt/EV write through to DS/Core) execute under the selector lock; surgery = detach the handler around locked mutations and do one manual refresh+raise after release, or compute the change set under the lock and apply it outside. (4) Chart-manager plot-model setters (earned-value/Gantt/resource charts) and `ResourceTrackerSetViewModel.RefreshIndex` raise inside their locks - trivial set-under-lock/raise-after splits. (5) Document the global lock-acquisition DAG in ARCHITECTURE §7 (Manager→Core→DisplaySettings, Core→Selector, node/tracker VMs as leaves; verify core never calls back into the scenario manager under its lock) so future cross-VM calls have an order to conform to. Adjacent smells noted while investigating: `GanttChartShowConnections`/`EarnedValueShowResources` are plain `List<int>` mutated by UI handlers without the DS lock while `SetValues` seeds them under it (torn-read risk), and DS setters mark the scenario dirty even when `RaiseAndSetIfChanged` is a no-op write. Related: the 2026-08-04 contention entry above - the getter sweep already delivered its "lock-free snapshots for hot bound properties" suggestion for the selector/tracker getters. **DIRECTION TO EXPLORE - delete locks rather than order them** *(2026-08-17)*: the reactive cascade itself is not the problem and does not need rewriting - in all three dumps the dependency graph behaved correctly and the failures were in the locking wrapped around it - but the current design is safe only by discipline, not by construction, because three properties combine badly: one lock per view model with cross-view-model calls made freely in both directions; synchronous notification (`PropertyChanged`/`CollectionChanged`) that re-enters arbitrary foreign code holding locks we neither own nor can inspect (ReactiveUI `ExpressionChainSink` gates, DynamicData, Dock); and `Scheduler.CurrentThread` subscriptions that run on whichever thread happened to raise, so "which thread executes this" is not statically knowable. The lock graph is therefore not fully knowable either, and a deadlock stays one refactor away no matter how carefully rules 6 and 9 are applied. Target end state: view models are UI-thread affine and hold NO locks at all, while background work (parse, compile, metrics) operates on immutable snapshots - as the compiler already does when it clones the graph - and returns a single result applied on the UI thread; with no locks there is no lock order to get wrong and rule 9 becomes unnecessary rather than merely enforced. Pragmatic 80% if full affinity proves too invasive on the load path: exactly ONE lock at the Core/model boundary and none anywhere else, which (combined with rules 6 and 9) removes every cycle among our own locks by construction. The path is incremental and mostly already walked - the getter sweep permanently killed the first class, the setter hoists killed the live instance of the second, and once rule 6 holds everywhere most remaining view-model locks will be found to guard nothing but brief field writes that only ever happen on one thread, at which point they can be DELETED rather than ordered (strictly better than maintaining a documented lock DAG forever, and it subsumes item 5 above). Add mechanical enforcement instead of vigilance: `System.Threading.Lock` exposes `IsHeldByCurrentThread`, so debug-only assertions at the raise/callback boundaries turn a latent deadlock into a loud test failure rather than a dump weeks later. Finally, the "third dump" (`zametek-deadlock-2.dmp`, 2026-08-17 - NOT a deadlock: no thread blocked on any lock, UI thread idle, while a scenario-load worker span inside `PriorityListResourceScheduler.CalculateResourceSchedules` with nothing ever scheduled onto any of the 14 resource builders) is no longer parked: the 2026-08-18 ClrMD analysis root-caused the spin as a torn `HashSet` clone poisoning the scheduler's `Contains` gate (ARCHITECTURE §7 rule 10 tells the full story and names the ProjectPlan-side race that tore it), the scheduler itself now detects the dead state upstream (Zametek.Maths.Graphs 3.2.0 reports compilation error C0020 instead of spinning, and `Compile` takes a cancellation token), and the app-side compile watchdog (`CompilationTimeoutMilliseconds`, 2026-08-19) bounds anything the scheduler cannot prove dead. The remaining structural item from that paragraph - run the compile outside the lock against a snapshot - is Phase 2 of the compile-on-snapshots entry below.

- [ ] **Run the compile outside `m_Lock`** *(2026-08-19, Phase 2b of the live-activity data-race work)* - Phases 1 and 2 both landed 2026-08-19: the deferred settings callbacks that corrupted a compilation's input are gone (ARCHITECTURE §7 rule 10), and a compilation now snapshots the plan, compiles a throwaway copy of the graph, and publishes the results back through `SetCompiledValues`, with a leaf lock making the snapshot and publish passes exclusive with the activities' own writes (§7 rule 11). What remains from the original design is the piece deliberately split out: `RunCompile` still holds `m_Lock` across the compile itself, so a long compile still blocks every UI binding that touches the core, and a non-terminating one still wedges it (bounded now, but only by the watchdog). The compile no longer needs that lock - it runs entirely on private copies - so this is now a small change: take `m_Lock` for the snapshot, release it for the compile, retake it to publish and assign `GraphCompilation`. What needs thought is what happens when compilations overlap once they are no longer serialised by the lock: either a second compilation is dropped while one is in flight (`IsReadyToCompile` already arms rather than queues, so this is close to today's behaviour), or the later result wins and the earlier is discarded - and either way `CompilationOutputRevision` and `HasStaleOutputs` must still describe the compilation that was actually published. Worth doing with the compile-cancellation seam in mind: with the token already plumbed through, superseding an in-flight compilation could cancel it rather than let it run to completion. Verify with the same before/after comparison used for Phase 2 (`zpp -i <file> -o <out>`, diff the output ignoring `ModifiedOn`, across all sample projects and several scenarios), plus the concurrency tests in `CoreViewModelCompilationTests`.

- [ ] **Bring the browser head up to the desktop application** *(2026-08-21)* - `Zametek.ProjectPlan.Browser` now presents the whole application: the dock layout, the data grids, the interactive graphs and the ScottPlot charts all render under WebAssembly. What remains is the behaviour behind them. (1) ~~**Split `MainView`**~~ - DONE 2026-08-21: it is now a `UserControl` shell shared by both heads, with `Zametek.ProjectPlan.Desktop.MainWindow` as the thin `Window` wrapper carrying the title, icon and closing-confirmation handlers; `File | Exit` became a `MainView.ExitRequested` event the host decides how to honour, and `MainView.CanExit` hides the item where no host window exists. (2) **Make the file layer work in streams** - the agreed design, and the single biggest piece. `IDialogService.ShowOpenFileDialogAsync`/`ShowSaveFileDialogAsync` return a local path, and `IProjectFileOpen`, `IProjectFileSave`, `IProjectScenarioFileImport`/`Export`, `IXlsxScenarioFileImporter`/`Exporter` and `IMicrosoftProjectFileImporter` all take a `string filename` and open it directly; a browser has no paths, only opaque `IStorageFile` handles that must be streamed. Desktop and CLI adapt to the same stream-based contracts. `BrowserDialogService`'s two file methods throw until this lands, deliberately: returning null would be indistinguishable from the user cancelling. (3) **Persist settings.** `BrowserSettingService` holds everything for the lifetime of the page; back it with localStorage or IndexedDB so the dock layout, grid layouts, recents and preferences survive a reload. Note that `ISettingService` is itself path-shaped (`SettingsFilename`, `DockLayoutFilename`, `ProjectDirectory`, `RecentProjectFilePaths`), so this is partly a contract question rather than only an implementation one - and the recents list cannot hold paths at all in a browser, since a handle the user granted access to is not a name that can be reopened. (4) **Turn off floating dockables** - `DockFactory` sets `CanFloat = true` on 17 dockables, and floating creates host windows the browser has none of. Untested so far: dragging a tool out of the layout is the obvious way to find out what actually happens. (5) **Confirm the diagnostic channel.** The head configures Serilog to the console with errors routed to stderr, but no Serilog output (nor plain `Console.WriteLine`) was observed reaching the browser console during bring-up, so the only place a browser-side failure can currently report itself is the page itself. Worth settling, because a web app that fails silently shows a blank canvas and nothing else. (6) **Prune what a browser cannot use** - `Process.Start` in `UriHelper` (use the browser's own navigation), `PerfTelemetry`'s file-writing thread, and hide MS Project import from the UI rather than letting it reach `UnavailableMicrosoftProjectFileImporter`. (7) **Check `System.Drawing.Common`** - a direct `PackageReference` in `Zametek.ViewModel.ProjectPlan` that no code appears to use, and which throws on any non-Windows platform; if it really is unused, delete it.

- [ ] **Decide how the web app is hosted and deployed** *(2026-08-21)* - `dotnet publish` produces a static `AppBundle`, but nothing publishes it anywhere. Two requirements are already known and documented in the README: a secure context (HTTPS or localhost) for the browser APIs the file pickers need, and a `Service-Worker-Allowed: /` header on `_framework/sw.js` - or that script served from the site root - because Avalonia registers its service worker at the root scope and without it Firefox and Safari lose the save-file fallback. Worth deciding alongside: whether the release workflow publishes the bundle as an artefact, whether it is served from GitHub Pages (which cannot send custom headers, so the sw.js placement matters) or somewhere that can, and whether Brotli precompression is worth configuring given the payload includes the whole runtime.

- [ ] **Reconsider single-threaded WebAssembly once the browser head does real work** *(2026-08-21)* - the browser head runs single-threaded, which is what lets it be served from any static host. The consequence is that every `Task.Run` in the view-model layer - and there are many, including `RunCompile` - executes on the UI thread, so a large plan's compile will freeze the tab, and the compile watchdog (`CompilationTimeoutMilliseconds`) probably cannot fire at all, since its timer callback has no thread to run on while a synchronous compile holds the only one. Neither has been measured yet; measure with a real plan before deciding. The alternative is `WasmEnableThreads`, which keeps `Task.Run` genuinely off the UI thread and restores the watchdog, at the cost of requiring COOP/COEP headers from the host (ruling out plain GitHub Pages) and a less well travelled Avalonia configuration. Related: the "delete locks rather than order them" direction in the rule-6 entry above becomes more attractive if the browser stays single-threaded, since a UI-thread-affine view model layer has nothing to contend over.

- [ ] **Stop the MSIX build depending on whether NuGet decides to restore** *(2026-08-21)* - the packaging build needs every project's `project.assets.json` to carry a target for each RID in the bundle, and `build-msix.ps1` arranges that by setting `RuntimeIdentifiers` in the environment so that restore populates all three in one pass. That only works if restore actually runs. When it does not - NuGet reports "All projects are up-to-date for restore" and keeps whatever assets file is already there - a file left behind by an ordinary `dotnet build`, which has no RIDs at all, survives, and the per-RID inner publish then fails with `NETSDK1047` naming a project that looks entirely innocent. Observed once during the `PlatformTarget` investigation, on `Zametek.ProjectPlan.Core`, immediately after a plain solution build; the run before and the run after both succeeded, which is what makes it look like flakiness rather than a missing input. Deleting `obj` in `-Clean` would force a restore and close it, and was tried on 2026-08-21, but it does not work: MSBuild evaluates every project before running any target and that evaluation imports `obj\<project>.nuget.g.props`, so against an empty `obj` the DesktopBridge targets fail with `MSB4024` looking for a file the same command is about to write. Splitting restore into its own invocation fixes that but then leaves the per-RID targets unpopulated, because the `RuntimeIdentifiers` environment variable does not reach a standalone `/t:Restore` the way it reaches the `/restore` switch; and passing it as a global property instead is worse still, since the per-RID inner publishes cannot then override it and the SDK rejects the whole list as a single identifier (`NETSDK1083`). All three failures are recorded in the script's comments so the next person does not walk the same three steps. What remains worth trying: `-p:RestoreForce=true` on the existing single invocation, which costs a few seconds of re-evaluation on a build already measured in minutes and would make the RID targets unconditional; or, cheaper and less certain, reading each referenced project's assets file up front and failing early with a message that names the real problem instead of letting `NETSDK1047` misdirect.

- [ ] **Audit the packaging path for more silently-inert code** *(2026-08-21)* - `-Clean` in `build-msix.ps1` never deleted anything from the day it was written: it used `Get-ChildItem -Path $dir -Include bin,obj -Directory`, and `-Include` filters the leaf of `-Path` rather than the children unless the path itself ends in a wildcard, so the pipeline matched nothing while the script cheerfully printed "Cleaned obj/bin". Nothing failed, which is precisely why it went unnoticed for a year - and it quietly invalidated every "clean build" anyone believed they had run, including the first comparison in the `PlatformTarget` investigation, where stale IKVM native staging made 64 files look as though a change to a managed compiler switch had rearranged the JDK. The packaging projects sit outside the solution filter, so nothing in the gates builds or exercises them, and the same class of fault - a command that appears to work because its failure mode is silence - could be sitting in the rest of that path. Worth a read-through of `build-msix.ps1`, the two `.wapproj` files and the WiX project with that specific suspicion in mind, and worth asking whether any of it can be brought under a gate.
